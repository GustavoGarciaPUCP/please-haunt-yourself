# Application recovery — the application is the encounter

November6,2026. Codex proposal responding to the participant's explicit correction. This replaces the one-shared-theatre/show recommendation as the product direction. The working ECHO theatre remains a preserved workshop; it is not relabeled as a finished application-recovery encounter. No global novelty/winner claim.

## The missing value

The earlier console affected a different scene but never had an illness, an interior, an ending or restored behavior of its own. Adding coaching, commands or more colors did not close that gap. The new loop is **observe a program's distinctive malfunction → enter its own system → change the cause → return and ask/check → use the visibly changed program**. A generic minigame pasted behind each app would repeat the same mistake.

## TERMINAL: The line that would not end

The recovered shell contains an old numbered BASIC-like session attributed to the fictional operator Mara, dated31October1987. Its human line is “I'll finish in a minute.” An exit callback keeps relaunching that line as executable work. We do not invent a biography, assert a real person's death, or make bereavement the whole puzzle. The mystery is why an ordinary last line never got to become history.

Initial shell: dark green CRT cues, a ghost caret/legacy transcript, visible local `last.session` PID3087 and contaminated responses. Typed `ask status` answers according to actual state; supported questions are discoverable and deterministic, not a claimed language model. Existing supported commands remain usable and input is never stolen/deleted by a timed scare.

`enter last.session` (or Enter session button) transforms the **same terminal window** into a playable execution trace, not another app alongside it. The same input/output, archive and exit hook appear as three connected instruction surfaces. The player's cursor is a debugger/interrupt, not a platform character walking to an exit. A Step execution action reveals one causal stage at a time without requiring a minimum number of steps before intervention.

There are three different interventions, all reversible through Undo:

- Disconnect stdout: old printing goes quiet while the exit loop still exists. A read-only status check distinguishes silence from repair.
- Disconnect the archive: erase the operator's retained line. This is an actual memory choice, not an automatic win/failure. If the restart hook remains, empty work still repeats.
- Disconnect the exit hook: prevent the next revival. Ask the current process to finish with TERM; a forced stop skips cleanup and leaves a residue, which can be resumed and closed cleanly. Process restarts change PIDs; stale targets are rejected.

The trace is an inspectable causal model: read archive → print line → schedule restart. Cut connections change subsequent trace output. Terminate while restart remains and it comes back, even if stdout was muted. A clean exit after disconnecting the hook produces either **settled with an archived memory** or **settled with a blank archive**, both valid endings. The choice changes the final terminal response and inspectable archive. No timer, permadeath or penalty for Undo.

Return to shell is always possible before solving. It is not success. After a clean release, green haunt treatment/duplicate caret/legacy interruptions disappear; the normal shell uses a quieter blue/ivory treatment and responds without reprinting the old line. `ask are you okay`/`ask status` acknowledge what actually happened: kept memory versus erased memory, still looping versus muted, or residual unclean stop. `cat last-session` exposes exactly what was retained. Closing/reopening the app preserves the current page's recovery; reload resets this prototype unless persistence is explicitly implemented later. `restore terminal` resets this encounter independently of the mirror workshop.

## Design test, not automatic agreement

The mechanism must be legible by observing a trace, not merely choosing a button labeled “repair.” Avoid random glitch text, a compulsory tragic biography, guess-the-magic-word dialogue or equating a muted screen with healthy software. The three actions need distinct observed results; the recovery must alter both appearance and behavior. The two successful endings must remain recoverable and honestly acknowledged. This is a bounded debugger encounter, not arbitrary operating-system command execution.

## Implemented slice and verification

`legacy-session.ts` is the independent application state model; `legacy-view.ts` projects its execution/connection trace inside the existing terminal window. Shell/internal navigation preserves identity and state. Muting, removing the saved line and detaching the exit callback change distinct model properties. Step execution exposes READ/PRINT/return behavior and new-PID revival. TERM after detaching the callback releases the session; KILL leaves recoverable residue. At END without the callback, the trace remains paused awaiting release instead of inventing another scheduled copy.

The saved line is an actual inspectable artifact: retained text versus a blank archive. Both clean outcomes update the terminal's skin, check-in response and normal `echo` behavior. Returning alone awards nothing and does not automatically ask a question; the player can explicitly type a supported question or press Are you okay. Undo, resume residue and restore terminal provide explicit recovery. App close/reopen preserves state in this page; a reload currently resets it. Existing mirror services are independent and their workshop retains its controls. The version2 onboarding introduces TERMINAL's own problem rather than immediately directing the player to ECHO.

## Critical limits after implementation

This closes the missing **inside application → intervention → return → changed function** loop for one program. It does not make the other applications recovered, nor prove that the encounter is unprecedented, outstanding or prize-worthy. The connection labels are deliberately legible; experienced users can infer the callback solution quickly. The optional execution trace supplies evidence rather than an arbitrary mandatory sequence, but three switches are still a small puzzle. Preserving/erasing the line changes an actual artifact and acknowledgement, not the entire OS story. A more expressive scene, wider consequences and human enjoyment testing are still needed. The future app table is a design constraint/candidate, not five invented completed implementations.
