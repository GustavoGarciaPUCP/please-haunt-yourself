## Codex's position

The existing ghost/bell encounter is a useful introduction. Its current small set of switches does not supply the expressive interaction or variety sought for the whole desktop. More ghost dialogue, more buttons or four versions of the same bell puzzle would not resolve that.

Programs should have individual personalities and native interactions while inhabiting one consistent fictional system. Their connection must be visible through causes, data and changed behavior. They do not need to share one room or the same control panel. A message written by a ghost can be evidence of something the player just did, rather than an unrelated spooky overlay.

The previous live-signal/frozen-memory candidate is incomplete on its own: it did not settle who rings the bell, why it recalls the session or why an image operation could affect a running request. Kiro must resolve those questions before treating the metaphor as a game model. A photograph cannot magically stop execution merely because it is a quest item.

Current source distinguishes the terminal-owned LegacySession from the older ProcessSession shared with the ECHO workshop. The old mirror/process connection exists; that does not make the newer ghost/bell encounter an integrated ECHO case. Do not describe the repository as having no connections at all, or count its unrelated mirror controls as a completed version of this proposal.

## A concrete candidate: an unfinished request, not a random haunting

Proposed rule for the first two-app case: TERMINAL has an unfinished request to ECHO. An active source reference keeps supplying completed-cycle updates; a completed cycle triggers one return notification, represented by the bell. This is not one bell per video frame or per render. The spirit is recalled when that request is reissued. A stored still preserves content without requesting further updates. This is a deliberately simplified fictional system, not a claim about how real terminals or cameras behave.

The player must establish which reference is active, deliberately create a usable still from the current session, and replace the live reference before completing the request. A capture alone does not replace anything; a muted bell does not close the request; pausing a preview does not stop its producer. Those distinctions must be demonstrated, not lectured.

Important objection: this remains small if the correct sequence is always Capture -> Finish and there is no real interpretation or consequence. Opus must strengthen or replace it if comparing sources, testing an intervention and choosing the retained state do not produce meaningful agency. Do not add arbitrary locks or require a perfect animation frame to conceal this weakness.

### Example player-visible sequence, to refine before implementation

1. **Inside TERMINAL:** the normal prompt starts normally. The application appends an unclaimed output line: `HELP ME.` Then: `I can reach the door. Something keeps calling me back.` It does not type into or replace the player's input.
2. **First demonstration:** the existing apparition tries to leave; the bell recalls it. ECHO's source indicator records the same return event. The doorway is an explanation of the session's state, not a separate unrelated minigame.
3. **ECHO becomes necessary:** opening its monitor reveals the current source and a bounded recording of that event. TERMINAL can report that a request remains open; ECHO can show which visual source and retained frame are involved. Neither supplies the other's entire answer.
4. **A plausible wrong experiment:** the player pauses ECHO's preview. Its picture freezes, but the request is still active. The next relevant return produces a new TERMINAL line: `You stopped the picture. Not the call.` A visual explanation works with audio off. The player can resume and compare; this is recoverable evidence.
5. **A consequential intervention:** the player captures an actual still, distinguishes it from a live source card and chooses which reference the pending request will retain. Retaining a live reference visibly continues updates; retaining a still removes the ongoing subscription. The artifact is real session data, not a prewritten trophy awarded regardless of action.
6. **Confirmation through normal functions:** TERMINAL can finish, its prompt no longer adds haunted output and its ordinary supported `echo` operation works. ECHO can preview/export the actual retained frame without restarting the haunting. Asking the ghost how it is now produces a response consistent with the intervention, not the same reply for every path.

This is an example, not mandatory verbatim dialogue or an approved final puzzle. Opus must define exact sources, permitted actions, causal ordering, the wrong experiment's trigger and the outcome model. If the causal rule cannot be explained plainly and implemented consistently, propose a better one before coding.

## What connects the three existing elements

| Element | Meaning in this candidate | Exclusive player capability | Visible proof |
| --- | --- | --- | --- |
| TERMINAL | The unfinished job/request and its returned output | Inspect/complete the current request and see what reference it holds | Output/check-in/normal commands change with actual request state |
| ECHO | The source, preview and capture studio | Compare the relevant event and create a non-live artifact from this session | Paused preview, live reference and stored still behave differently |
| Bell | A return notification that accompanies reissuing the request | Its mute/visual state may be inspected; it is not a third program | One shared event is visible in both apps; silencing does not fake completion |

The actual model, not animation timing, decides when a return occurred. The two views must not invent independent bells or increase the return tally twice for the same event. Replaying a recorded event must not emit a new live return. Closing/minimizing an app is UI lifecycle and must not silently count as a successful exorcism.

## Contextual ghost writing and motion

- Prefer a small authored set of state-aware lines over random `HELP ME` spam. Example triggers: first return, preview paused while a request stays active, live reference submitted, still accepted, forced interruption, recovery.
- The content must follow what actually happened. Never say the player muted the bell if they only paused a preview. Persistent facts and one-shot presentation cues are different data.
- Append to a bounded in-app transcript. Never overwrite selection/input, imitate the real operating system or take over focus. New output should not drag a person away from older text they are reading.
- Keep user-driven window movement immediate. A ghost line and the matching ECHO evidence can share a short visual accent; avoid unrelated simultaneous blinking, shaking and popups.
- Reduced motion displays complete text and static state evidence. Every important event is understandable with sound off. Let the player revisit the evidence without waiting for another automatic scare.
- Hidden/minimized views must not keep creating unsolicited dialogue/cues. A model event may remain reviewable on return; it must not reapply gameplay effects just because a view remounts.

## Evaluation and competition fit

The official Costume Contest description asks for polished, memorable spooky UI whose spooky elements enhance function. The published design criterion asks for a coherent complete experience, and innovation asks how it differs from existing concepts. The proposal should therefore be evaluated through native actions and a working causal demonstration, not numbers of apps, lines or effects. [Official event requirements and criteria](https://kiroween.devpost.com/)

Fictional computer interfaces already have published predecessors: Hypnospace Outlaw's official page describes investigating a detailed fictional internet. That is a genre precedent, not a hands-on comparison with our build or proof that the proposed mechanic has already been done. Distinctive evidence here would be the implemented relationship between a haunting, the program's real controls and the player's retained artifact. Do not claim this is unprecedented or that this analysis predicts a prize. [Developer's Hypnospace page](https://www.hypnospace.net/)

Acceptance requires an unaided PC walkthrough of the actual chosen design, a plausible wrong intervention with understandable feedback, two genuinely different native app capabilities, persistence/lifecycle correctness and a concrete before/after comparison. A simulated novice review is not human enjoyment research. Four planned programs do not count as four completed experiences.
